# İETT static bus data operations

The public bus catalogue uses a separate, small, immutable package for line, stop and planned-departure data. It is generated by the WordPress transit sync after the verified transit package is available. Live vehicle locations and service alerts are not stored in this package.

## Data boundary

The package serves these public features without an İETT request on each visit:

- bus-line list and search;
- line detail, route stops and planned departures;
- stop detail, passing lines and nearest-stop lookup;
- bus entries in site search, sitemap and IndexNow.

`/api/iett/konum` remains the live vehicle endpoint and continues to call the live provider. `/api/iett/duyurular` also remains a live alerts endpoint. Planned departures are derived from the active verified transit snapshot and are labelled **Planlanan**; they are not live arrival predictions.

## Package layout and integrity

```text
current.json
previous.json
versions/<version>/manifest.json
versions/<version>/directory.json.gz
versions/<version>/lines/<sha256(line-code)>.json.gz
versions/<version>/stops/<sha256(stop-code)>.json.gz
```

Every pointer identifies a manifest SHA-256. The manifest inventories every compressed shard with its exact byte count and SHA-256. The frontend validates the pointer, manifest, gzip member and payload contract before returning data. If any current-package component fails, the reader retries the complete operation against `previous.json`; it never mixes current and previous shards.

The CMS manifest records the two bulk SOAP source URLs, retrieval times, source byte counts and SHA-256 values, plus the transit snapshot pointer used for schedules. Source calls are one bulk `GetHat_json` request and one bulk `DurakDetay_GYY_wYonAdi` request per refresh. There is no per-line schedule download.

## Configuration

Production frontend:

```dotenv
IETT_STATIC_BASE_URL=https://cms.hizliulasim.com/wp-content/uploads/hizliulasim-iett-static/
```

The variable is server-only. Do not expose it as `NEXT_PUBLIC_*`. Production requires an HTTPS URL. Local development and tests may instead use `IETT_STATIC_STORAGE_PATH`; production deliberately rejects a local path so a missing volume cannot silently become a partial deployment.

CMS defaults to `wp_upload_dir()/hizliulasim-iett-static`. These optional values override it:

- PHP constants `HIZLIULASIM_IETT_STATIC_STORAGE_PATH` and `HIZLIULASIM_IETT_STATIC_PUBLIC_BASE_URL`;
- environment variables `IETT_STATIC_STORAGE_PATH` and `IETT_STATIC_BASE_URL`.

The work directory and publication root must be on the same filesystem because final installation uses atomic rename. Serve mutable pointers with `no-cache` or a very short TTL. Serve `versions/*` with long-lived immutable caching without changing the inventoried gzip bytes.

## Refresh and failure policy

Run the manual **Toplu Ulaşım Veri Eşitleme** once a week. Also run it after a known İETT line/stop timetable revision. Live vehicles and alerts are separate, so increasing this static refresh frequency does not make those features more current.

The final bus stages shown in the panel are:

1. line download;
2. stop download;
3. normalization;
4. planned-schedule derivation;
5. package staging;
6. full validation;
7. atomic publication.

An error before publication leaves the existing `current.json` unchanged. Once bus publication starts, cancellation is disabled. A lost poll or retry can reuse verified source artifacts, checkpoints and an already moved immutable version. Do not delete an active work directory or hand-edit a checkpoint.

If the package cannot be read at all, static API routes use the existing upstream implementation through one shared five-minute cache. Responses expose which path was used:

- `X-Hizliulasim-Data-Source: iett-current`;
- `X-Hizliulasim-Data-Source: iett-previous`;
- `X-Hizliulasim-Data-Source: iett-legacy`.

Package responses also include `X-Hizliulasim-Data-Version` and `X-Hizliulasim-Data-Generated-At`. The bus UI displays the update time and clearly marks previous-package or legacy fallback use.

## Publication and rollback

Deploy the CMS producer first. Complete one successful sync and verify the package over its intended HTTPS origin before setting the frontend environment variable and deploying the frontend.

For a rollback, with no active sync, run an operator script inside the real WordPress context that obtains `hizliulasim_iett_static_with_lock()`, reads `previous`, verifies it with `hizliulasim_iett_static_verify_pointer()`, then atomically installs it as `current` with `hizliulasim_iett_static_install_pointer()`. Check every `WP_Error`. Do not edit pointer JSON manually and do not modify an immutable version directory.

After publication or rollback, verify:

- `current.json` and `previous.json` parse and point to different known-good versions when a previous version exists;
- both manifest hashes and representative line/stop shard hashes match;
- mutable and immutable cache headers are correct;
- the six static `/api/iett/*` routes report a package source;
- `/api/iett/konum` still behaves as a separate live call.

## Verification commands

Frontend focused checks:

```powershell
node --test src/lib/iett-static/contracts.test.ts src/lib/iett-static/source.test.ts src/services/iett-static.test.ts src/app/api/iett/static-routes.test.ts src/lib/iett-static/presentation.test.ts
npx tsc --noEmit
npm run build
```

CMS focused checks, from a shell with the repository mounted at `/app`:

```sh
php tests/transit-data-iett-static-source.test.php
php tests/transit-data-iett-static-materializer.test.php
php tests/transit-data-iett-static-publisher.test.php
php tests/transit-data-checkpoint.test.php
php tests/transit-data-sync-admin.test.php
```

Fixture tests prove contracts and recovery behavior; they do not prove live-host filesystem atomicity, HTTP caching, CORS, source availability or a real production package. Record those separately during the first server run.
